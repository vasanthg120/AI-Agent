01 Executive Summary

The short version, before the evidence.

Haive is a real, working, multi-tenant SaaS product — not a demo. It has bcrypt+JWT auth with session revocation and 2FA, a genuine multi-tier CRM integration against an external product called ProspectConnect, a working Microsoft Graph OAuth2 flow with encrypted token storage, a metered credit-billing system wired to Stripe/Razorpay/Cashfree, an org-scoped RAG pipeline over Qdrant, and a Claude-based tool-calling agent loop that can read and write real CRM, calendar, email and WhatsApp data. This is materially more built than a typical "AI chat wrapper."

The README is stale by roughly a month of active development (README.md last touched 2026-07-19; app/agent/orchestrator.py 2026-08-17) and describes a system that no longer exists: it claims an OpenAI + Gemini router, but the code runs on Anthropic Claude + Groq (app/agent/anthropic_client.py, app/agent/groq_client.py — no OpenAI or Gemini client file exists anywhere in the repo). It claims the CRM and Outlook modules are "stubbed" placeholders; both are real integrations today. It claims Redis is unused; a per-tool rate limiter and a cache module both read/write it. Anyone onboarding from the README alone would misjudge the system in almost every direction — some features are far more real than documented, one (web search) is less real than documented.

The product has quietly grown past "AI sales agent" into a full retail/franchise operations suite — billing, royalty (franchise revenue-share), vendor management, finance documents, gamification, timeline, command-center, and business-intelligence modules sit alongside the CRM/chat core. This is a legitimate strategic direction, but it also means engineering effort is spread across ~31 backend modules while the two areas that most directly gate revenue — lead/deal intelligence and test coverage on anything except billing — are comparatively thin.

There is no first-class "Lead" concept. The product speaks ProspectConnect's own vocabulary — contacts, deals, accounts, quotes — and approximates lead-funnel tracking through email-intent classification (email-preclassification.util.ts) feeding an "enquiry-conversion" analytics view. There is no lead score, no qualification stage, no assignment workflow, and no agent tool that can create or update a deal (only list/search tools exist for CRM data — see §8).

Autonomous business action is real but unconfirmed. The agent can send real email (SMTP) and real WhatsApp messages (Meta Cloud API) once credentials are configured, and the tool registry (app/tools/registry.py) enforces schema validation, per-user rate limiting and persona-scoped tool allow-lists on every call — but there is no human-in-the-loop confirmation step before a side-effecting tool fires. A model that decides to email a customer, emails them.

Testing and CI are the sharpest gap. 16 of 16 backend spec files sit inside auth/ and billing/; the CRM, chat, memory, RAG, business-intelligence, royalty, finance, gamification and integrations modules — the majority of the product surface — have zero automated tests. The Python agent and the frontend have none at all. There is no .github/workflows directory, so none of this is even checked on push.

04 Backend Audit

NestJS 10 · Mongoose · 31 modules, 70 controllers, 73 schemas.

Auth uses two entirely separate Passport strategies — JwtStrategy for customer users and AdminJwtStrategy for a distinct AdminAccount collection — sharing only the JWT secret, never the user model. Both re-fetch the account on every request rather than trusting the token's snapshot claims, so deactivation and role changes take effect on the next call instead of waiting out the token TTL (strategies/jwt.strategy.ts:29-52). Session revocation is real: each login issues a jti appended to the user's sessions[]; a token whose jti no longer appears there is rejected — genuine logout-everywhere / revoke-a-device support, not just TTL-based expiry.

Security-conscious details worth keeping

  • Global ValidationPipe({whitelist, forbidNonWhitelisted, transform}) in main.ts — unknown/extra body fields are rejected outright.
  • Razorpay webhook HMAC is verified against the literal raw request bytes (rawBody:true in main.ts), not a re-serialized JSON body — the correct way to do it.
  • CORS is an explicit configured origin with credentials:true, not a wildcard.
  • A documented, already-fixed privilege-escalation bug: sales-target.controller.ts's achievement route previously had no role guard, letting any authenticated user query org-wide or a named coworker's revenue figures via query params — the comment trail shows this was caught and closed, a good sign for how seriously the team treats access control.

What's incomplete

backend/src/outlook/outlook.service.ts:87-99 — placeholderEmails() is returned whenever the mailbox isn't "configured", and also as the unconditional fallback path even when it is. The OAuth handshake, token storage/refresh and agent-side consumption are all real; this one surfaced read is not.

Multi-model routing, correctly implemented

trivial_router.py sends short/simple turns to Groq; anything already mid-tool-loop, long, or tool-shaped goes to Claude via anthropic_client.py. personas.py layers a second dimension on top — each configured agent persona carries its own system prompt, allowed-tool allow-list, and model tier, and that allow-list is enforced twice: once by only exposing those tool specs to the model (registry.get_tool_definitions), and again as a hard check inside execute_tool() — so a persona restriction can't be bypassed even from the MCP server path (app/mcp_server.py), which exposes the same tool registry to external MCP clients.

06 AI / LLM Audit

Distinguishing "a good prompt" from "an agent that acts."

The system genuinely crosses the line from text generation into tool-driven action: CRM reads, SMTP sends, WhatsApp sends, and memory writes are all real side effects a model can trigger mid-conversation, gated only by schema validation, a 30-calls/minute-per-tool rate limit, and persona scoping — not by any confirmation step (see §11). crew_reports.py runs a second, separate execution path (CrewAI, pinned to 0.130.0 specifically because newer CrewAI drags in a Starlette version this FastAPI app can't tolerate) purely for the scheduled morning/EOD report — the live chat loop never touches CrewAI. Reasoning is bounded, not open-ended: the tool-round cap is 5 per turn (app/agent/orchestrator.py), a sane guardrail against runaway loops and runaway spend.

Prompt management lives in app/prompts/registry.py and definitions.py as versioned, named prompt definitions rather than inline strings scattered through the codebase — a real practice, not just convention.

10 Database & Data Architecture Audit

73 Mongoose schemas across the backend — organizations, users (with embedded sessions[] for revocation), CRM cache, billing/subscriptions/invoices/coupons, royalty, finance, gamification stats, timeline events, notifications, agent roles. Qdrant holds four semantically distinct point namespaces via source_type payload filtering — document (user-private uploads), finance_document and business_knowledge_document/ business_profile (org-wide), and memory (per-user long-term facts) — a clean, consistent tenant-isolation pattern rather than one shared unscoped bucket (app/rag/retriever.py). Redis backs the tool-call rate limiter and a cache layer for cacheable ProspectConnect reads (app/cache/, prospectconnect.py's _CACHEABLE_PATHS).

Missing for a production sales agent: no dedicated lead entity/collection (§8); no "agent execution history" collection distinct from tracing spans (§7); index coverage on the 73 schemas was not individually audited — flagged ❓ rather than assumed adequate.

12 Performance & Scalability Audit

  • Single in-process scheduler. main.py's BackgroundScheduler (RAG sync, CRM/quote Mongo sync) is explicitly documented as safe only for a single python-agent replica — horizontal scaling the agent needs this moved to a real job queue (Redis is already present) before it's safe.
  • Synchronous billing round-trip on every turn. reserve() is a blocking HTTP call to the backend before the LLM call even starts, adding real latency to every message; acceptable at current scale, worth watching under load.
  • Tool round cap (5) and per-tool rate limit (30/min/user) bound both cost and latency blowup — good defaults, not yet load-tested per this audit.
  • Conversation history growth — no summarization/compaction step was found feeding _build_messages(); long conversations will grow the context sent to the LLM unbounded (a real cost and latency risk as usage grows).

13 Code Quality Audit

Code quality is notably above average for a project this size — comments consistently explain why (a documented ProspectConnect quirk in crm_deal_tool.py, the CrewAI/Starlette pin conflict in requirements.txt, the Windows console encoding workaround in main.py), and several comments record a bug that was found and fixed rather than just the current state. The main structural risks are scale-driven, not craft-driven: 31 backend modules and 20 agent tools is a lot of surface for a small team to keep coherent, and the near-total absence of tests outside billing (§14) means that discipline currently rests entirely on code review, not on a safety net.

14 Testing Audit

2/31backend modules tested

16 spec files total: 1 in auth/ (admin-auth.spec.ts), 15 in billing/. Every other backend module — CRM, chat, dashboard, gamification, timeline, business-intelligence, royalty, finance, vendors, integrations, documents, notifications, organizations, users — has zero automated tests. The Python agent has no test_*.py anywhere. The frontend has no .test./.spec. file anywhere.

Minimum bar before production: auth (already covered) plus (1) the chat→agent→tool round trip with a mocked LLM, (2) the billing reserve/settle/release state machine under concurrent requests, (3) CRM credential-resolution tiering (the exact bug class the code comments show already bit production once), (4) RBAC on every role-gated endpoint, and (5) tenant-isolation on RAG retrieval (a leak here is a cross-customer data breach, not just a bug).

15 DevOps & Deployment Audit

  • Dockerfiles exist for all three services plus the nested submodule copy; frontend/nginx.conf serves the built SPA.
  • docker-compose.yml is a single, dev-shaped file — no separate hardened production compose/K8s manifests were found.
  • No CI/CD — no .github/workflows directory exists anywhere in the repo. Nothing runs tests, lint, or a build check automatically on push or PR.
  • Only the Mongo service has a healthcheck in compose; backend/agent/frontend containers have restart: unless-stopped but no liveness/readiness probes wired to it.
  • No backup, monitoring/alerting (Prometheus/Grafana/Sentry), or rollback strategy was found in-repo — this may live outside the repository, so it's marked ❓ rather than asserted absent.

18 Broken Features

19 Missing Features

20 Features to Modify

Add a confirmation/dry-run gate for side-effecting tools (email/WhatsApp send, CRM writes) before they fire unattended · replace outlook.service.ts's unconditional placeholder-email fallback with a real Graph read now that the OAuth plumbing already exists · give the billing fail-open path an explicit cap/alert rather than silent unmetered pass-through · move the in-process scheduler to a queue-backed job runner ahead of any horizontal scale-out.

21 Features to Remove

Nothing rises to "delete this" — the mock fixtures found (§3) are small, honest, and low-risk enough to leave as-is. The clearest cleanup candidate is documentation, not code: the README needs a rewrite (§1), and the purpose of the frontend/AI-Agent submodule needs to be either documented or removed before it accumulates more silent drift.

22 Recommended Target Architecture

The existing shape is already close to right — frontend → backend gateway → agent orchestration → LLM → tool router → external systems → activity → memory. The gap is not in the layers, it's in two places: (1) a confirmation checkpointActivity/Memory write-back step after every tool execution, so the next turn (or the next day's autonomous run) can see what the agent already did rather than re-discovering it from scratch each time.

23 Future Memory Architecture

Keep the existing dual-write pattern (Mongo as system of record, Qdrant as the semantic mirror) and extend it with two new layers rather than replacing anything: an Episodic Activity collection (one document per tool execution: what was called, on whose behalf, what changed, keyed by organization + lead/deal id) written directly from execute_tool()'s existing success path, and a Semantic Business Memory collection for durable org facts ("our standard payment terms are Net 30") distinct from the current CRM-sync RAG index, which is transactional data, not knowledge. Both should carry organization_id as a mandatory field from day one, following the isolation pattern already used correctly by rag/retriever.py's per-source_type filters.

24 Product Capability Gap Analysis

The platform's engineering maturity (auth, billing, multi-tenancy, real integrations) is well ahead of its stated product vision (an autonomous sales/RevOps agent). The gap is concentrated almost entirely in the lead layer: everything downstream of "a lead exists" — scoring, prioritization, stale-deal detection, proactive outreach, forecasting — is either approximated through email-intent classification or simply absent, while everything upstream (auth, billing, tenancy, integrations, analytics plumbing) is unusually solid for this stage. This is a favorable gap to have: the hard infrastructure is done, and what's missing is domain logic that can be built on top of it.
